# Развёртывание на china: перенос с turkey и команды владельца

Документ описывает, как бот оказался на текущем сервере, что в нём добавилось сверх базовой функциональности
скачивания и какие грабли встретились. Написано 27–29.09.2026 по факту выполненных работ.

## 1. Что произошло

Бот жил на VDS «turkey». 17.09.2026 хостер потерял сервер, дальше трижды менял IP, и после каждой смены
сервер оставался без **исходящей** связи при живой входящей — для бота это смертельно (не может дотянуться
до Telegram). 24.09.2026 всё хозяйство (MTProto-прокси, AmneziaWG VPN и этот бот) перенесено на сервер
**china** (Alibaba Cloud, Гонконг, Debian 12, 1.7 GB RAM).

Перенос бота:

```bash
# на старом сервере — исходники и тома
tar czf - -C /home/amnezia telegram_yt-dlp | ssh china 'tar xzf - -C /home/admin'
sudo tar czf - -C /var/lib/docker/volumes telegram_yt-dlp_shared telegram_yt-dlp_botapi-data \
  | ssh china 'sudo tar xzf - -C /var/lib/docker/volumes/'
```

Путь на сервере: `/home/admin/telegram_yt-dlp` (на turkey было `/home/amnezia/...`).

## 2. Грабли переноса

### Сборка образа из Китая идёт часами

`apt-get install ffmpeg` тянет ~200 пакетов с `deb.debian.org`, из Китая это 8 секунд на пакет: за 25 минут
скачалось 182 штуки и конца не было. Лечится зеркалом Aliyun — правка в `Dockerfile`:

```dockerfile
RUN sed -i s@deb.debian.org@mirrors.aliyun.com@g /etc/apt/sources.list.d/debian.sources || true; \
    apt-get update && apt-get install -y --no-install-recommends ffmpeg curl \
    && rm -rf /var/lib/apt/lists/*
```

После этого установка пакетов занимает ~4 минуты. Оригинал сохранён рядом как `Dockerfile.orig`.

### telegram-bot-api падал с Permission denied

Том `telegram_yt-dlp_botapi-data` перенесён архивом под root, и владелец файлов не совпал с пользователем
внутри контейнера (uid 101). Симптом — рестарт-цикл с `PosixError : Permission denied : File
"/var/lib/telegram-bot-api/tqueue.binlog"`. Лечение:

```bash
sudo chown -R 101:101 /var/lib/docker/volumes/telegram_yt-dlp_botapi-data/_data
```

Если ошибка не уходит — хранилище пересоздаётся само: остановить сервис, переименовать `_data`, создать
пустой каталог с владельцем `101:101`, запустить. Это очередь и кэш, данные бота не теряются.

### EXTERNAL_URL указывал на мёртвый адрес

В `.env` оставался IP самого первого сервера, то есть ссылки на скачанные файлы не открывались задолго до
переезда. При смене сервера этот параметр нужно править вручную — он нигде не выводится и молча ломается.

## 3. Что добавилось: команды владельца

Бот получил приватный интерфейс к панели MTProto-прокси. Все команды работают **только** для аккаунта
владельца и **только** в личке; для остальных пользователей их не существует — сообщение уходит в обычные
хендлеры скачивания. Меню команд регистрируется через `BotCommandScopeChat`, поэтому другие его не видят.

| Команда | Что делает |
|---|---|
| `/status` | здоровье прокси и VPN: версия, проблемные проверки, кто онлайн, сканеры, сертификат, домен |
| `/stats` | трафик всех пользователей прокси за сутки |
| `/stats <имя>` | подробно по человеку: трафик 24 ч/7 д, отношение вниз/вверх, дни активности, VPN-пир |
| `/vpn` | пиры VPN: статус, последнее рукопожатие, трафик |
| `/config` | выдать ссылку прокси или файл `.conf` VPN; создать нового пользователя/пира |
| `/cancel` | отменить ввод имени при создании |

Файлы: `bot/status.py` (сводки), `bot/provision.py` (выдача и создание доступов).

### Архитектура: бот ничего не делает сам

Вся работа с ключами и конфигами — на стороне панели (`proxy-monitor` на хосте, порт 1080). Бот только
рисует кнопки и отдаёт результат. Это сделано намеренно: у контейнера бота нет и не должно быть доступа к
Docker-сокету и файлам хоста.

```
бот (контейнер) ──HTTP──> панель (хост, :1080) ──> docker exec / конфиги / БД
```

Эндпоинты панели, которыми пользуется бот:

| Метод | Путь | Токен | Назначение |
|---|---|---|---|
| GET | `/api/stats` | нет | всё состояние для `/status`, `/stats`, `/vpn` |
| GET | `/api/provision/list` | нет | список пользователей прокси и пиров VPN |
| GET | `/api/provision/vpn/<имя>` | нет | текст `.conf` существующего пира |
| POST | `/api/provision/vpn/add` | **да** | создать пира (без перезапуска VPN) |
| POST | `/api/provision/proxy/add` | **да** | создать пользователя прокси (перезапускает прокси) |

Панель слушает `0.0.0.0:1080` и доступна всем пирам VPN, поэтому операции создания защищены заголовком
`x-api-token`. Токен лежит на сервере в `/home/admin/dashboard/api-token` (права 600), боту передаётся
переменной `PANEL_TOKEN`.

### Важное про создание

- **VPN-пир добавляется без перезапуска**: ключи генерируются внутри контейнера, применяются на живом
  интерфейсе (`awg set`), дописываются в `wg0.conf`. Никого не обрывает.
- **Пользователь прокси требует перезапуска** прокси — обрыв у всех на несколько секунд. Прокси читает
  список пользователей только при старте. Бот предупреждает об этом до ввода имени.

## 4. Новые переменные окружения

```
PANEL_URL=http://host.docker.internal:1080   # панель на хосте
OWNER_ID=<telegram id владельца>             # узнать у @userinfobot
PANEL_TOKEN=<из /home/admin/dashboard/api-token>
```

Чтобы `host.docker.internal` резолвился из контейнера, в `docker-compose.yml` добавлено:

```yaml
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

Без `OWNER_ID` команды владельца просто не регистрируются — бот работает как обычная качалка.

## 5. Порядок регистрации хендлеров имеет значение

В `bot/__main__.py` модули импортируются в таком порядке:

```python
from bot import status      # команды владельца — ПЕРВЫМИ
from bot import provision
from bot import handlers    # обычный функционал
```

Исторически это было обязательно: хендлер ручного ввода формата в `handlers.py` с регуляркой
`^[\w+\-/\[\]<>=.,*]+$` ловил любой короткий текст со слэшем, включая `/status`, молча ничего не делал и не
пропускал сообщение дальше — при обратном порядке команды владельца не отвечали вообще, без ошибок в логах.

С 29.09.2026 причина устранена: регулярка стала `^(?!/)...` (текст, начинающийся со слэша, не совпадает), а
при отсутствии ожидающей сессии хендлер делает `raise SkipHandler` и отдаёт сообщение дальше. Порядок
импортов оставлен как есть, но больше не критичен.

## 6. Обслуживание

```bash
# пересборка после правок
cd /home/admin/telegram_yt-dlp && docker compose up -d --build

# долгая сборка не должна рваться вместе с ssh
sudo systemd-run --no-block --unit=botbuild --collect \
  --working-directory=/home/admin/telegram_yt-dlp /usr/bin/docker compose up -d --build

# логи без шума от веб-сервера
docker logs --since 10m telegram_yt-dlp-bot-1 2>&1 | grep -v 'GET / HTTP'
```

Бэкап исходников бота и томов делается ежедневным `/home/admin/backup.sh` вместе с остальным хозяйством;
копии в `/home/admin/backups/` (14 штук). Ручной бэкап перед правками:

```bash
tar czf /home/admin/backups/bot-src-$(date +%Y%m%d-%H%M).tgz bot docker-compose.yml .env Dockerfile
```

## 7. Ограничения

- **getUpdates чужим кодом запрещён.** Бот забирает обновления long-polling через локальный
  `telegram-bot-api`; параллельный запрос `getUpdates` с тем же токеном отберёт у него апдейты (ошибка 409).
  Поэтому `chat_id` владельца получен вручную через @userinfobot, а не автоматически.
- **Токен работает и через облачный API.** Несмотря на `log_out()` при старте (переключение на локальный
  сервер), `sendMessage` через `https://api.telegram.org` тем же токеном проходит — этим пользуется отдельный
  скрипт уведомлений о здоровье прокси (`/home/admin/alerts/alerts.py`), он шлёт только владельцу.
- Бот и панель живут на одном сервере; если панель недоступна, команды владельца отвечают
  «⚠️ панель недоступна», а скачивание продолжает работать.
